Критерий 2. Соблюдение горизонта 10–15 минут и раннее
предупреждение (0-4)
● Прогноз/алерт стабильно формируется в окне T+10…15 минут до события —
основа балла.
● Нет «прогнозов задним числом» (алерт после наступления сбоя); в
идеале указывается предполагаемое время опоздания и причина.
● Горизонт соблюдается на потоке, а не только на офлайн-выгрузке.
Критерий 3. Работающая система из 3 модулей + запуск в Docker (0-6)
● Решение упаковано в Docker-контейнеры и поднимается по одной инструкции.
● Чётко выделены ML-ядро (инференс/обучение) и Backend (API,
оркестрация) — не монолит; API работает (Swagger отвечает на пробный
запрос).
● Backend принимает и парсит поток телеметрии NDTP, сопоставляет с
расписанием и считает производные признаки (текущее отклонение,
средняя скорость на сегменте, время простоя).
● Связь модулей рабочая end-to-end: поток → прогноз → дашборд.
Критерий 4. Диспетчерский BI-дашборд (0-6)
● Понятность за ~5 секунд: диспетчер видит проблемные ТС/участки без
инструкции.
● Карта маршрутной сети с текущим положением ТС и цветовой индикацией
риска (зелёный/жёлтый/красный).
● Карточка инцидента: ТС с высокой вероятностью задержки,
прогнозируемое опоздание, предполагаемая причина, участок
маршрута.
● Данные обновляются в реальном времени вслед за потоком.
Критерий 5. Производительность и надёжность (0-4)
● Пропускная способность: поток ТС обрабатывается без накопления очередей.
● Деградация при обрывах связи: сервис не падает, переходит на
исторические данные / последнее состояние и восстанавливается после
реконнекта.
● Холодный старт Docker-контейнеров предсказуем. Балл снижается при
отсутствии подтверждений, но не обнуляется при корректной архитектуре.
