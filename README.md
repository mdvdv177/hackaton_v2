# Предиктор отклонений городского транспорта

Независимые Backend, ML-сервис и веб-дашборд принимают NDTP, сопоставляют GPS
с плановыми посещениями и прогнозируют подписанное отклонение прибытия.
Цель — первая ещё не посещённая остановка в **(T+600 с, T+900 с]**.
Горизонт отсчитывается до **планового** прибытия и повторно проверяется
перед публикацией. Ретроспективная оценка отделена от предупреждений.

## Запуск

Требуется работающий Docker Engine с Compose. Готовые CPU-модели обоих профилей
находятся в `artifacts/models/`. Из корня проекта:

```bash
docker compose up --build -d --wait
```

Если Docker Desktop установлен на macOS, но `docker compose` отсутствует в PATH,
используйте `python3 -m scripts.stack up`. Скрипт проверяет Engine, Compose
и модели, собирает и запускает стек, не меняя глобальную конфигурацию Docker.

- Дашборд: **http://localhost:8088**.
- Backend Swagger: **http://localhost:8010/docs**.
- OpenAPI: **http://localhost:8010/openapi.json**.
- Состояние и очереди: **http://localhost:8010/api/v1/system/status**.
- Метрики: **http://localhost:8010/metrics**.
- NDTP TCP: **localhost:9211**; внутри Compose — `backend:9201`.

Порты и пароль БД задаются в `.env`, пример — `.env.example`. PostgreSQL и ML
доступны только внутри Compose. `python3 -m scripts.stack down` сохраняет БД.
После рестарта исторический прогон восстанавливается **на паузе**, NDTP продолжает
работу с сохранённым сценарием. Поддерживается один Backend-воркер.

## Режимы работы

1. **Исторический прогон** в интерфейсе: исходные данные 6 января 2026 года,
   часы сценария, пауза и скорости ×1/×5/×20. Режим оценки использует официальные
   контрольные точки и не создаёт текущие предупреждения.
2. **NDTP-демо на текущую дату**: `make demo-ndtp` после установки Python-зависимостей
   и запуска стека. Скрипт сдвигает расписание и времена исходной телеметрии одним
   смещением и отправляет реальные TCP-пакеты в темпе ×1. Manifest хранит исходное
   время, новую точку отсчёта и SHA-256 источника. `Ctrl+C` останавливает отправитель.
   Для запуска уже собранного стека вместе с отправителем:
   `.venv/bin/python -m scripts.demo_ndtp --start-stack`. Приложение после остановки
   отправителя продолжает работать; запуск демо создаёт новый активный прогон.
3. **Собственные данные**: импортируйте JSON-сценарий в интерфейсе и выберите его
   перед запуском NDTP. Без актуального расписания и привязок устройств live
   не подменяет данные январским test-набором.

Импорт версионирован: одинаковый пакет даёт тот же ID, изменение содержимого
создаёт новую неизменяемую версию. Проверка без сохранения:

```bash
curl -fsS -X POST 'http://localhost:8010/api/v1/scenarios/import?dry_run=true' -H 'Content-Type: application/json' --data-binary @scenario.json
```

Формат и пример: [сценарии и импорт](docs/scenarios.md).
Вся сеть загружается независимо от выбранного ТС. Если предоставлены только
остановки, линии обозначены как **схема по расписанию**. Импорт поддерживает
справочники остановок, маршрутов, рейсов и направленную геометрию сегментов.

## Модели и измеренное качество

| Профиль и протокол | Точки | MAE, с | Нулевой baseline, с |
|---|---:|---:|---:|
| `official`: предоставленный `cur_dev_s` | 353 | **70,61** | 103,34 |
| `stream`: причинные признаки, все точки диагностически | 353 | **80,58** | 103,34 |
| `stream`: свежие, ещё не посещённые цели | 340 | **81,58** | 103,95 |

В потоке используется `stream` со схемой признаков `2.0.0`: посещения, оценка
отклонения и скорость сегмента вычисляются общим `CausalObserver` только по
событиям, **возникшим и полученным к T**. Модель выбрана по временным train-folds
с зазором 30 минут; OOF MAE 87,83 с. Test не использовался для выбора модели.
Калибровка вероятности `delay > 120 с` обучена на OOF; test Brier stream — 0,13430.

Официальные модель, схема `1.0.0` и submission сохранены. `artifacts/submission.csv`
содержит 151 уникальную точку, UTF-8, разделитель `;`, колонки
`sample_id;prediction`, включая допустимые отрицательные значения.
Отчёты: [official](artifacts/report.json), [stream](artifacts/stream_report.json),
[причинная оценка](artifacts/stream_evaluation.json).

Это оценка контрольных точек одного периода. Test и validate имеют одинаковую
телеметрию; качество на новых днях и скрытый score платформы не измерены.
MAE официального протокола нельзя обещать в живом потоке.

## Настройка официального CatBoost

Отдельный поиск 50 конфигураций с временными разбиениями и однократным
подтверждением кандидата:

```bash
.venv/bin/python -m ml.tune --data-dir dataset --baseline-model-dir artifacts/models --output-dir artifacts/tuning/official-20260927-01 --trials 50 --seed 20260926
```

Нужны Python-зависимости из `make install`. Результаты нового поиска пока
не измерены; улучшение не гарантируется. Поиск использует CPU с двумя потоками,
предполагает более 200 обучений и сохраняет результат в отдельном каталоге,
сохраняя текущие модели и submission. [Правила поиска и принятия](docs/tuning.md).

## Разработка и проверки

Требуются Python 3.12+ (проверено на 3.13), Node.js 22+ и Google Chrome для
браузерных проверок. Установка и воспроизведение:

```bash
make install
make test
make frontend
make docs
make train-stream          # потоковый профиль
make train                 # официальный профиль
make submit
.venv/bin/python scripts/dev.py
```

Локальный frontend: `http://127.0.0.1:5173`, Backend использует SQLite.
При одновременном запуске с Docker задавайте свободные порты.

```bash
make acceptance-ui         # 11 изолированных сценариев браузера
make acceptance-cold       # 3 запуска с новой БД, NDTP → ML → SSE → браузер
docker load -i dataset/ndtp-telemetry-emulator.tar
make acceptance-ndtp       # полный путь через поставленный NDTP-эмулятор
make acceptance-faults     # NDTP/ML/БД/Backend: отказ и восстановление
make acceptance-warm       # диагностика полной 15-минутной истории, около 5 минут
make acceptance-load       # 100 ТС × 1 Гц, час; два всплеска 500 событий/с
.venv/bin/python scripts/check_demo_ndtp.py  # исходные CSV через NDTP → браузер
.venv/bin/python -m scripts.report_acceptance # сводка; график при наличии измерений нагрузки
```

Приёмочные Docker-проверки создают собственные проекты, свободные порты и новые
volumes, затем удаляют только их. Нагрузочный тест измеряет получение GPS →
отрисовка и запуск расчёта → отрисовка в настоящем браузере. Короткий прогон
с `--seconds 120` считается диагностикой. Итоги и ограничения —
[в протоколе проверки](docs/validation.md).

Часовая проверка окончательной сборки отложена по указанию пользователя:
`artifacts/acceptance/load-status.json`. Команда формирования отчёта только читает
сохранённые измерения и записывает сводку; нагрузку она не запускает.

`acceptance-warm` ускоренно доставляет прошлые события за 180 с, затем проверяет
120 с обычного потока и несколько новых прогнозов каждого ТС. Он выявляет
замедление на накопленной истории, но не заменяет `acceptance-load`.

Старые `smoke.py`, `benchmark.py`, `check_resilience.py` предназначены для
ручной диагностики и могут переключать основной прогон; для приёмки используйте
команды выше.

## Границы подтверждения

Реальная маршрутная геометрия и рейсовые справочники не предоставлены;
реализован и проверен их импорт, но соответствие карте города требует этих
данных. Проверка понятности за 5 секунд подготовлена, человеческие ответы ещё
не получены. Причины задержки показаны как гипотезы, модельные факторы не доказывают
причинность. Решение рассчитано на локальную демонстрацию; публичное размещение
требует аутентификации, TLS и ограничения управляющих API.
