# Инструкция для жюри

## 1. Запуск и доступ

Из корня клонированного репозитория выполните:

```bash
docker compose up --build -d --wait
docker compose ps
```

Ожидаются четыре здоровых сервиса: `backend`, `ml`, `frontend`, `postgres`.
Три первых — модули решения, PostgreSQL — инфраструктура хранения.
Дашборд: **http://localhost:8088**. Swagger: **http://localhost:8010/docs**.
Другие порты можно задать в `.env` по `.env.example` до запуска.

## 2. Подать исторический поток без дополнительных инструментов

1. Откройте дашборд и выберите «Диспетчерский replay».
2. Выберите ×1 и нажмите «Запустить replay»; для уже сохранённого прогона —
   «Продолжить». ×5/×20 ускоряют виртуальные часы, «Пауза» останавливает их.
3. Наблюдайте рост счётчика телеметрии и изменение позиций ТС. Данные взяты
   из `dataset/test/traffic.csv` и расписания; исходные файлы не изменяются.
4. Выберите ТС в списке или на карте. Прогноз появляется при свежих данных
   и наличии ещё не посещённой цели в окне `(T+600 с, T+900 с]`.

«Ретроспективная оценка» предназначена для контрольных точек official-модели.
Она не создаёт живых алертов; для проверки диспетчерских предупреждений
используйте «Диспетчерский replay» или NDTP.

## 3. Подать настоящий NDTP из исторического датасета

Для отправителя нужен Python 3.12+; установка в отдельное окружение:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m scripts.demo_ndtp --duration 60
```

Скрипт создаёт новый активный NDTP-прогон, переносит план и исходную телеметрию
на текущую дату одним смещением и отправляет двоичные пакеты по TCP на
`localhost:9211` в реальном темпе ×1. Он сам включает live-прогон: дополнительно
нажимать «Подключить поток» не нужно. Откройте дашборд, выберите режим
«Живой поток NDTP» для соответствия панели управления активному прогону.

В терминале появляются `started`, затем `progress` с `sent` и
`model_predictions`. В проверенном 60-секундном сценарии отправлены 102 пакета,
первый прогноз на экране появился за 3,646 с. Это измерение конкретного запуска,
а не гарантированное время на любом компьютере. Для длительной ручной демонстрации
уберите `--duration 60`; `Ctrl+C` останавливает только отправитель.

После прекращения потока через 60 секунд ТС становится серым, последняя позиция
сохраняется, текущая вероятность скрывается. Новый сценарий заменяет активный
прогон, но не удаляет историю из БД. Подробности: [демонстрация](docs/demo.md).

## 4. Поставленный организаторами эмулятор NDTP

Архив образа предоставляется организаторами отдельно и не хранится в Git.
Если он доступен, положите его в `dataset/ndtp-telemetry-emulator.tar`:

```bash
docker load -i dataset/ndtp-telemetry-emulator.tar
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m playwright install chromium
PLAYWRIGHT_CHANNEL=chromium .venv/bin/python -m scripts.check_ndtp
```

Проверка поднимет отдельный Docker-проект, импортирует явно синтетическое
расписание текущей даты, настроит эмулятор и проверит путь NDTP → модель →
SSE → браузер. В конце выводится `passed: true`; результат находится в
`artifacts/acceptance/ndtp_official.json`. Временный проект удаляется,
основной дашборд не переключается. Это тест интеграции, не точности на прибытиях.
При установленном Google Chrome можно пропустить установку Chromium и выполнить
последнюю команду без `PLAYWRIGHT_CHANNEL=chromium`.

Для своего источника импортируйте актуальный JSON-сценарий по
[контракту](docs/scenarios.md), выберите его и нажмите «Подключить поток».
Устройства должны соответствовать привязкам сценария и отправлять NDTP на
`localhost:9211`; эмулятор внутри Compose использует `backend:9201`.

## 5. Где увидеть прогнозы и алерты

- В списке и на карте виден текущий риск: красный — вероятность задержки
  больше 120 с не менее 70%; жёлтый — вероятность не менее 40% либо
  опережение более 60 с; серый — нет актуальных данных или допустимой цели.
- Карточка ТС показывает подписанное отклонение, плановое и ожидаемое прибытие,
  вероятность, время прогноза и целевой участок «от → до».
- «Движение, факторы и рекомендация» раскрывает наблюдения и гипотезу причины.
  Текущий участок движения может отличаться от участка целевого прибытия.
- В журнале инцидентов откройте конкретную строку и нажмите «Просмотрено».
  ACK относится к выбранному инциденту, сохраняется в БД и не изменяет риск.
- Отсутствие красного алерта допустимо: модель не обязана предсказывать высокую
  вероятность для каждого транспорта. Для просмотра прогноза выберите любое
  ТС с актуальной модельной карточкой.

Горизонт относится к **плановому**, а не гарантированному фактическому прибытию.
Предупреждения, опоздавшие за границу горизонта, подавляются. Карта без поставленной
геометрии отображает подписанную схему, а не восстановленные реальные дороги.

## 6. Метрики, документация и submission

```bash
curl -fsS http://localhost:8010/health/ready
curl -fsS http://localhost:8010/api/v1/system/status
curl -fsS http://localhost:8010/metrics
```

Первый запрос должен вернуть `status: ready`. Во втором доступны состояния
сервисов, счётчики телеметрии/прогнозов, глубина очередей и задержки; третий
возвращает Prometheus-метрики. Ответ без ошибок на `/health/ready` не заменяет
проверку появления реального прогноза. Дополнительно: `docker compose logs --tail 50 backend ml`.

- [Sphinx и статические Swagger/OpenAPI](https://mdvdv177.github.io/hackaton_v2/).
- [Производительность и реализованные возможности](PERFORMANCE.md).
- **[Файл для загрузки в Data Science](artifacts/submission.csv)**: 151 строка,
  `sample_id;prediction`, UTF-8. Знак прогноза сохраняется.

Остановить стенд с сохранением данных: `docker compose down`.
Часовой нагрузочный тест в инструкции не запускается.
