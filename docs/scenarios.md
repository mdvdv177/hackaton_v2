# Расписание, привязки устройств и маршрутная сеть

Сценарий объединяет плановые посещения, привязки NDTP-устройств и необязательную
геометрию. Исходные CSV не изменяются. Backend принимает только разрешённые поля;
`time_fact_begin`, целевые значения и неизвестные поля не переносятся в сценарий.

## Минимальный пакет

Сохраните JSON в `scenario.json`. Время в примере демонстрационное: перед живым
запуском укажите свой актуальный план и настоящий ID устройства.

```json
{
  "schema_version": "1.0",
  "source_id": "city-dispatch",
  "name": "Маршрут 1 · прямое направление",
  "timezone": "Europe/Moscow",
  "device_bindings": {"900000": "bus-1"},
  "planned_visits": [
    {
      "tt_action_item_id": "visit-1",
      "tr_id": "bus-1",
      "time_begin": "2026-09-26T12:00:00+03:00",
      "geom": "POINT (37.6000 55.7000)",
      "building_address": "Остановка А"
    },
    {
      "tt_action_item_id": "visit-2",
      "tr_id": "bus-1",
      "time_begin": "2026-09-26T12:13:00+03:00",
      "geom": "POINT (37.6100 55.7100)",
      "building_address": "Остановка Б"
    }
  ]
}
```

В UI используйте «Импорт JSON»: интерфейс сначала выполняет проверку, затем
сохраняет прошедший её пакет. Эквивалентный REST-путь:

```bash
curl -fsS -X POST 'http://localhost:8010/api/v1/scenarios/import?dry_run=true' -H 'Content-Type: application/json' --data-binary @scenario.json
curl -fsS -X POST 'http://localhost:8010/api/v1/scenarios/import' -H 'Content-Type: application/json' --data-binary @scenario.json
curl -fsS http://localhost:8010/api/v1/scenarios
```

Возвращённый `scenario.id` передайте в
`POST /api/v1/live/start` как `{"scenario_id":"city-dispatch:<version>"}`.
При `schedule_mode=as_is` план должен содержать посещение в окне
`[сейчас−15 минут, сейчас+24 часа]`. Для текущего прогноза дополнительно нужна
цель в `(сейчас+10 минут, сейчас+15 минут]` и свежая телеметрия.
Один Backend обслуживает один активный сценарий; запуск другого создаёт новый
прогон, предыдущие записи сохраняются в БД.

## Импорт реальной геометрии

В каждый visit можно добавить `stop_id`, `route_id`, `trip_id`, `direction_id`
и целочисленный `sequence`. Соответствующие справочники обязательны при наличии
ссылок. Пример дополнительного поля верхнего уровня:

```json
{
  "network": {
    "stops": [
      {"id": "stop-a", "name": "А", "coordinates": [37.60, 55.70]},
      {"id": "stop-b", "name": "Б", "coordinates": [37.61, 55.71]}
    ],
    "routes": [{"id": "route-1", "name": "Маршрут 1"}],
    "trips": [{"id": "trip-1", "route_id": "route-1", "direction_id": "outbound"}],
    "segments": [{
      "id": "segment-a-b",
      "route_id": "route-1",
      "from_visit_id": "visit-1",
      "to_visit_id": "visit-2",
      "provenance": "Учебный пример; заменить геометрией перевозчика",
      "geometry": {
        "type": "LineString",
        "coordinates": [[37.60, 55.70], [37.605, 55.706], [37.61, 55.71]]
      }
    }]
  }
}
```

Геометрия — GeoJSON WGS84, порядок координат **долгота, широта**. Сегмент
связывает последовательные посещения одного ТС и рейса в направлении движения.
Его начало/конец должны находиться не далее 150 м от соответствующих visit.
Маршрут сегмента должен совпадать с маршрутом visit/рейса. Конфликт справочника
остановок и координат visit также отклоняется. Без `trip_id` посещения группируются
по ТС и UTC-дню; это схема порядка посещений, а не восстановленный рейс.

## Проверки и происхождение данных

- От 1 до 100 000 visits; уникальные ID посещений и справочников.
- NDTP unit ID — десятичное целое 0..2147483647, с однозначной привязкой к ТС.
- Время приводится к UTC. Локальное время использует `timezone`; неоднозначное
  время перехода DST требует явного смещения UTC.
- Координаты должны быть конечными и допустимыми. Отсутствующий `geom` разрешён,
  но соответствующее ребро не строится. Совпадающие точки и неоднозначный порядок
  сохраняются в `gaps`, без выдуманной геометрии.
- Все рёбра по одним лишь точкам имеют `geometry_kind=schedule_schematic`.
  Привязанный LineString — `supplied_route`; смесь источников — `mixed`.
  Поле `coverage` показывает число visits, сегментов и долю поставленной геометрии.
- Импорт проверяет согласованность, но не удостоверяет правдивость геометрии:
  её соответствие реальному маршруту подтверждает владелец данных.
- Версия — отпечаток нормализованного содержимого. Повторная загрузка идемпотентна;
  редактирование создаёт новую версию, существующая не перезаписывается.

## Сдвиг демонстрационного времени

`POST /api/v1/live/start` с `{"schedule_mode":"demo_rebased"}` создаёт отдельный
сценарий из безопасного test-плана. В `manifest` записываются `source_time`,
`wall_anchor`, постоянное `offset_s`, `source_sha256` и `demonstration=true`.
Команда `make demo-ndtp` использует ровно это смещение для event/receive time
исходной телеметрии и отправляет NDTP по реальным часам. Исходные CSV, интервалы
между посещениями и порядок по `receive_time` остаются неизменными.

По умолчанию исходная точка отсчёта — `2026-01-06T07:00:00Z`. Из test-телеметрии
выбираются 13 устройств, привязанных к test-плану; непривязанные строки явно
подсчитываются и пропускаются. Передача от этой точки продолжается около 21,4 часа
до конца исходных записей, без повторов и ускорения часов. `--duration 60`
ограничивает только работу отправителя; приложение остаётся запущенным.

`--warmup-seconds 900` отдельно включает загрузку прошлой истории: максимум
2000 событий за предыдущие 15 минут, до 100 пакетов/с. Это поздняя доставка
истории при запуске; её фактическое время приёма отличается от исходного.
По умолчанию warmup выключен. Подробные команды и ограничения точности NDTP
описаны в [сценарии демонстрации](demo.md).
