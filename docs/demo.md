# Сценарий демонстрации

## Подготовка и запуск

Команды выполняются из корня репозитория. Требуются Docker, подготовленное
Python-окружение `.venv` и оба артефакта модели: `artifacts/models/manifest.json`
и `artifacts/models/stream/manifest.json`. Установка зависимостей описана в
[README](../README.md). Если артефактов нет, обучите профили:

```bash
.venv/bin/python -m ml.train
.venv/bin/python -m ml.train_stream
```

Переносимый launcher сам находит доступный Docker Compose:

```bash
.venv/bin/python -m scripts.stack doctor
.venv/bin/python -m scripts.stack up
.venv/bin/python -m scripts.stack ps
```

После healthcheck откройте http://localhost:8088. Backend и Swagger доступны
на http://localhost:8010/docs, NDTP TCP — `localhost:9211`. Сборка требует
доступа к реестрам зависимостей; фоновые тайлы карты загружаются извне.
При отсутствии тайлов остаются координаты, остановки и схема участков.

## Постоянное демо через настоящий NDTP TCP

В отдельном терминале запустите отправку исходной test-телеметрии:

```bash
.venv/bin/python -m scripts.demo_ndtp
```

Команда создаёт **новый активный прогон** `demo_rebased`, получает от Backend
manifest переноса плана и использует ровно то же смещение для телеметрии.
Исходный срез по умолчанию — `2026-01-06T07:00:00Z`. Пакеты отправляются
по исходному receive time в масштабе 1×; Backend фиксирует фактическое время
их приёма. Хеш источника и смещение проверяются до отправки. Исходные CSV
остаются неизменными.

В исходном test-наборе однозначно привязаны к плану 13 устройств. Записи без
такой привязки отправитель учитывает отдельно и пропускает; случайная подмена
ID другого ТС не выполняется. Это отличается от синтетического нагрузочного
сценария на 100 ТС.

Отправитель работает до конца данных или `Ctrl+C`; приложение и контейнеры
после его завершения остаются запущенными. Переключение прогона в UI останавливает
этого отправителя. Для ограниченного показа используйте `--duration 60`;
для запуска уже собранного стека вместе с отправителем — `--start-stack`.
После обычного запуска отправителя дополнительно нажимать «Подключить поток»
не нужно: это создало бы другой прогон.

По умолчанию предварительная история не загружается. Прогнозы появляются,
когда поступила свежая телеметрия и есть первая ещё не наблюдённая цель через
10–15 минут. Для показа с предварительной историей доступен параметр
`--warmup-seconds 900`: он отправляет максимум 2000 прошлых событий с ограничением
100 пакетов/с. Это явно отмеченный startup backfill; время их фактического
приёма отличается от исходного расписания отправки.

Пропущенные GPS/скорость сохраняются как отсутствующие значения. Двоичный
NDTP имеет собственную точность: timestamp — целые секунды, скорость/курс —
целые значения; отсутствующий курс передаётся как 0. Этот демонстрационный
тракт не используется как официальный submission или независимый эталон MAE.

## Путь диспетчера

1. Убедитесь, что выбран «Живой поток NDTP», в полосе происхождения указано
   «Демо NDTP · время расписания перенесено», часы движутся по текущему времени,
   а счётчик телеметрии растёт. Вся доступная сеть показана до выбора ТС.
2. Найдите красное или жёлтое ТС в списке; при отсутствии таких сигналов
   выберите любое ТС с текущим прогнозом. Цвет участка означает риск прибытия
   к конечной остановке, а не подтверждённую пробку на дороге.
3. В карточке проверьте ТС, участок «от → до», время прогноза, подписанное
   отклонение, вероятность задержки более 2 минут, плановое и ожидаемое прибытие.
   Горизонт при публикации должен быть строго больше 10 и не больше 15 минут.
   Основные поля и подтверждение просмотра помещаются на экране 1366×768.
4. Раскройте «Движение, факторы и рекомендация»: текущий наблюдаемый участок
   и его средняя скорость могут отличаться от целевого участка прибытия.
   При недостаточном покрытии скорость отсутствует. Причина — наблюдение
   или гипотеза, которую должен проверить диспетчер.
5. Если есть инцидент, нажмите «Просмотрено». Отметка относится к выбранному
   инциденту; она не закрывает его и не меняет риск. Красный, жёлтый и зелёный
   меняются сразу при новом прогнозе, без ожидания нескольких обновлений.
6. В журнале откройте прежнюю цель через режим наблюдения/истории. Карточка
   должна показывать именно её участок, времена, причину и отметку просмотра,
   даже если у ТС уже другой текущий прогноз. Новые строки загружаются кнопкой
   продолжения журнала; количество в снимке может быть меньше полного журнала.
7. Остановите только отправитель через `Ctrl+C`. После 60 секунд без свежей
   телеметрии ТС станет серым, последняя позиция сохранится, текущая вероятность
   исчезнет. Старое значение задержки остаётся подписанным как последний прогноз.

Красный означает `p_late ≥ 70%`; жёлтый — `p_late ≥ 40%` либо опережение более
минуты. Серый означает отсутствие текущих данных/допустимого прогноза.
Прогноз старше 90 секунд становится нетекущим даже при свежих координатах.
Когда прежняя цель оказывается ближе 10 минут, она переходит в наблюдение.
Число красных ТС, список, карта и карточка используют один текущий риск Backend.

## Исторический replay и официальная оценка

Для исторической демонстрации выберите «Диспетчерский replay» и нажмите
«Запустить replay». Скорости ×1/×5/×20 меняют виртуальные часы; пауза их
замораживает. Здесь работают stream-профиль, причинный observer и фактический
receive-time cutoff. Быстрый replay не ослабляет проверку горизонта: если
расчёт опоздал, он подавляется, а не выдаётся за своевременное предупреждение.

«Ретроспективная оценка» использует официальный профиль, исходные T, цели
и предоставленный `cur_dev_s`. Она явно подписана как ретроспектива, не
показывает результат как текущую вероятность риска и не создаёт живые инциденты.
Для validate источник задаётся через API; запрос запускает новый прогон:

```bash
curl -fsS http://localhost:8010/api/v1/replay/start \
  -H 'Content-Type: application/json' \
  -d '{"mode":"evaluation","source":"validate","speed":20}'
```

Submission формируется отдельно, без восстановления validate-ответов из
пересекающихся расписаний:

```bash
.venv/bin/python -m ml.submit
.venv/bin/python -m scripts.evaluate_replay
```

Вторая команда оценивает замороженный stream-профиль по заданным test-точкам
и пишет `artifacts/stream_evaluation.json`. Общая диагностика и подмножество
допустимых свежих/ещё не наблюдённых целей имеют разные знаменатели.
Они не являются оценкой непрерывного живого NDTP-потока. Подробности и фактические
результаты — в [validation.md](validation.md).

## Импорт своего сценария

Подготовьте пакет по [контракту сценария](scenarios.md): актуальный план,
привязки unit ID к ТС и, при наличии, справочники маршрутов/остановок и геометрию.
Нажмите «Импорт JSON» и выберите файл. UI сначала выполняет dry run, затем
сохраняет прошедший проверку пакет; ошибки 422 показываются пользователю.
После успешного импорта выберите сценарий в режиме NDTP и нажмите
«Подключить поток». Это новый прогон `as_is`; импорт отдельно его не запускает.
Источник NDTP должен отправлять пакеты с указанными unit ID на порт 9211.

Для `as_is` Backend требует хотя бы одно плановое посещение в интервале
`[текущее время − 15 минут, текущее время + 24 часа]`. При отсутствии сценария
или подходящих плановых дат API отвечает 409. Кнопка выбора «Демо с согласованным
временем» создаёт перенесённый план, но сама не запускает процесс отправителя.

Сеть из расписания остаётся явно подписанной восстановленной схемой.
Импортированные LineString показываются как поставленная геометрия;
смешанное покрытие имеет отдельную подпись. Проверка реального совпадения
с дорожными маршрутами требует справочника и подтверждения владельца данных.

## Изолированные проверки и восстановление

Следующие проверки создают собственные Compose-проекты и освобождают их после
завершения. Для проверки поставленного эмулятора сначала импортируйте образ:

```bash
docker load -i dataset/ndtp-telemetry-emulator.tar
.venv/bin/python -m scripts.check_ndtp
.venv/bin/python -m scripts.check_cold_start
.venv/bin/python -m scripts.check_faults
```

`check_ndtp` проверяет полный путь поставленного эмулятора: двоичные пакеты,
согласованный синтетический план текущей даты, stream ML и доставку в браузер.
Это проверка интеграции, а не точности на реальных прибытиях. `check_cold_start`
проверяет запуск чистого проекта. `check_faults` воспроизводит разрыв NDTP,
отказ ML, временную недоступность PostgreSQL и аварийное пересоздание Backend.
Для браузерных проверок нужен установленный Chrome.

При восстановлении сохраняются `run_id`, сценарий, последние позиции,
наблюдения, durable inbox и ACK. Исторический replay после перезапуска находится
на паузе; NDTP продолжает жить по текущим часам. SSE запрашивает новый снимок,
если старый курсор уже отсутствует. При отказе ML возможен только явно отмеченный
baseline со свежим отклонением и без вымышленной вероятности.

Наблюдение за системой доступно на `/api/v1/system/status` и
http://localhost:8010/metrics. Healthcheck фронтенда —
http://localhost:8088/healthz. Остановка основного стека с сохранением данных:

```bash
.venv/bin/python -m scripts.stack down
```

Протокол проверки понимания экрана за пять секунд подготовлен в
[usability.md](usability.md). Его статус **NOT_RUN** означает, что участники
ещё не проходили проверку; автоматические снимки не заменяют человеческий тест.
