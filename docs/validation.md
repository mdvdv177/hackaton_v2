# Проверка исправленного решения

Ниже проверяются критерии 2–5 исходного задания: 14 подпунктов,
без самостоятельного назначения баллов жюри. Исходные задания и промежуточные
аудиты не входят в пакет сдачи; актуальные результаты приведены здесь.

Финальное часовое испытание отложено по указанию пользователя
(**DEFERRED_BY_USER**). После этого указания оно не запускалось; полночасовая
устойчивость окончательной сборки не подтверждена. Новых прогонов сейчас нет.

  включая 17 тестов настройки CatBoost, 2 проверки экспорта документации и
  точное сравнение оптимизированных
  признаков с прежним расчётом, причинные отсечения подготовленной истории,
  работу event loop при занятом ML worker и защиту приёмочного harness от ложного
  PASS. В этот запуск входят 9 тестов отдельного SQL-наблюдателя; время — 29,92 с.
- Frontend: production build в Docker выполнен; 11 браузерных регрессий проходят
  без JS-ошибок. Отчёт: `artifacts/ui_regressions/report.json`.
- Sphinx: сборка `-W` без предупреждений.
- Основной Docker-стенд обновлён с существующей БД; пять проверок реального UI

  без JS-ошибок. `artifacts/ui_check.json`; дашборд оставлен на паузе.

  время публикации не выдумывается. Проверено сохранение pending inbox и активного

  отложенного задания после новых посещений, границы горизонта после медленного
  ML/commit, немедленное снижение риска и точный ACK при сбое записи.
- Устранена гонка SSE между выдачей предыдущего снимка и ожиданием уведомления:
  наличие нового event ID проверяется под той же блокировкой перед ожиданием.
  Детерминированный тест сначала воспроизвёл задержку, затем прошёл с исправлением;

### Сохранённый протокол часовой нагрузки

- 100 устройств × 1 Гц, 3600 секунд настоящего времени.
- На 1200–1260 и 2400–2460 секундах — 500 событий/с.
- NDTP TCP → PostgreSQL inbox → reducer → настоящий stream ML → SSE → React.
- Никаких пропусков принятых событий; итоговая очередь должна опустеть.
- p95 получение → UI и запуск расчёта → UI ≤2000 мс.
- Модельное покрытие ≥99% первых допустимых целей с ≥30 с свежей доступности;
  baseline учитывается отдельно, не повышает модельное покрытие.
- После всплеска: возврат к очереди не более одного обычного тика (100 событий)
  и отставанию ≤2 с за 30 с. Последние 10 минут: медиана отставания ≤1 с,
  максимум ≤5 с.
- Наблюдаемый Backend RAM ≤1 GiB; медиана последних 15 минут не выше предыдущих
  15 минут более чем на 128 MiB. Docker stats снимается примерно раз в минуту;
  максимальный допустимый разрыв — 90 с, в каждом окне требуется ≥10 замеров.
  Это максимум сохранённых снимков, а не непрерывно измеренный пик. Проверка
  разницы медиан не доказывает отсутствие любой возможной утечки памяти.
- Проверяется устойчивость темпа самого отправителя. Показатель UI относится к
  новым состояниям, отображённым после объединения событий в снимок; UI не обязан
  отрисовать каждый GPS-пакет всплеска.
- После 60 с прогрева каждые 5 с проверяется поступление новых GPS-состояний
  всех 100 ТС за последние 10 с и новых модельных прогнозов за 60 с, свежесть
  SSE/React и совпадение прогона. Зависший UI, пропуск временного окна или
  недоотправленный всплеск не могут дать PASS. Хеши runtime сверяются с кодом,
  сохраняются ID образов и frontend-ассетов.

**Финальная часовая приёмка: DEFERRED_BY_USER.** Пользователь попросил
остановиться до её запуска. После этого указания финальный часовой тест
и его SQL-наблюдатель не запускались; дальнейших прогонов сейчас нет.
Короткие проверки и диагностика полной истории не подтверждают устойчивость
в течение часа с двумя всплесками и контроль длительного роста памяти.

Вторая длительная попытка `transport-load-a95a7ef7` остановлена после
1048,263 с: все 104 600 событий приняты и применены, ошибок отправителя и JS нет,

Прямая SQL-транзакция подтвердила **102 000 raw = inbox = applied = checkpoint,
pending=0**. Runtime-код соответствует исходникам, образы не менялись;
временный проект удалён. Отчёт и снимок:
`artifacts/acceptance/warm-history.json` и `.png`.
Ускоренное получение истории явно имеет `full_acceptance=false`: проверка
не заменяет час, два всплеска и контроль длительного роста памяти.

Первая попытка этой диагностики остановилась из-за расхождения wall clock и
monotonic-таймера отправителя; неполные измерения не засчитаны. Исправлены только
измерительный скрипт и его cleanup, добавлены регрессии коррекции часов и ошибки
задачи отправителя. Частичные промежуточные отчёты не включены в пакет сдачи;
они не используются как доказательство успешной проверки.

Отдельная SQL-сверка прерванной попытки успела подтвердить ровно 104 600 raw,
inbox, applied и checkpoint при pending=0. Её durable PASS относится только
к доставке этих событий; нагрузочный результат остаётся FAILED и неполным.
`artifacts/acceptance/load-durability-before-pipeline-optimization.json`.

Подготовлен отдельный SQL-наблюдатель: транзакция READ ONLY сверяет raw,
applied inbox и checkpoint с точным числом отправленных событий. В его протоколе
предусмотрен снимок примерно раз в 30 с и интервал 0,5 с с 3590-й секунды,
чтобы успеть прочитать БД до удаления временного проекта. Сейчас наблюдатель
не запущен; сохранённая выше сверка относится только к прерванной попытке.
PASS отдельного `PG.json` не подменяет сверку финальной часовой нагрузки.

### Границы устойчивости

`ingress_admitted` — принятие в оперативный буфер, `ingress_committed` — успешная
запись в PostgreSQL. NDTP здесь не предоставляет прикладного подтверждения
commit: авария до фиксации может потерять ещё не сохранённый пакет. Graceful stop
пытается сбросить буфер до 5 с. Подтверждённые inbox-записи и checkpoint применяются
транзакционно; после рестарта незавершённая работа читается повторно.

Холодный запуск считается с уже собранными образами и моделями, но новой БД.
Время загрузки Docker images и обучения в SLO ≤60 с не входит. Длительная
недоступность БД сверх ёмкости 5000 приводит к backpressure и явным счётчикам
отклонений, а не обещанию неограниченной безубыточной буферизации.
